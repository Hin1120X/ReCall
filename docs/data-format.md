# 数据格式与兼容规则（0.5.0）

数据库为本机 SQLite，结构版本7。事项 ID、记录 ID 和文件 ID 均为稳定 UUID；界面调整不改变归属和原始时间。

## 0.5新增关系、草稿与断点

`resource_groups` 保存资料与分组的多对多关系。任务与链接共用平面分组目录；省略 `groupIds` 保留旧关联，明确空数组才清空。普通文字检索不因关联分组名字匹配而展开所有成员；组内查询使用明确 ID，名称、别名与原位目标仍可检索。

`link_drafts` 独立保存快捷窗口／工作台共用的链接地址及分组草稿，不复用含附件令牌的任务草稿。主进程比较预期快照后才写入或清空，冲突保留原草稿。收藏链接与消费对应草稿在同一事务内完成；失败不清草稿。自动命名不请求网页，重名时自动分配序号。

`checkpoint:<事项ID>` 使用原草稿体系，保留未知扩展和待存附件；不会因简洁界面清空历史字段。保存断点使用事项版本检查，在一次事务内更新现场、可选下一步、追加 `notes.kind=checkpoint` 历史并清草稿。未输入下一步时保留原值，`lastProgressAt` 不改变。未处理附件的断点草稿保留并拒绝直接提交，不悄悄丢弃。

本地建议全量考虑未完成事项，再取最多三项；不读取已保存 AI 排序。`task_usage` 仅代表查看，`lastProgressAt` 及明确的 progress 记录才代表实际推进。旧现场没有来源时间时不借用 updatedAt 伪造时间。

## 0.4新增关系与周期

`catalog_entries` 统一保存 resource/group/person 三种目录条目，稳定 UUID；resource 保存受校验的本地文件/文件夹或 http/https 目标，名称、别名、固定、归档和最近使用可独立更新。修改名称或路径不改变关联。归档保留历史关系，不删除原文件。分组为平面多选，相关人为本地文本身份，不关联账号或发送消息。

`item_catalog` 以事项和目录 ID 保存多对多关系。保存前校验存在性和类型；省略关系字段保留旧值，显式空数组才清空该类关系。筛选按所选关系、文字、状态组合；默认全部未完成包含等待、暂停和未来提醒。检索可匹配正文、记录和关联名称/别名、拼音及首字母。`task_usage` 独立保存最近打开信息，查看不修改事项 updatedAt 或实际推进时间。

`items.recurrence` 保存类型、间隔及起点，`seriesId` 保存周期系列身份。完成事务中只生成一次独立下一事项，重复完成不会重复生成。按天/周/月沿本地日历起点找未来下一次，月末按原起点日恢复；完成后间隔天按完成时刻计算。复制正文、标签、分组、相关人、常用资料、原位引用、主文件夹与扩展属性；不复制旧历史、附件、现场、推进时间及截止。重新打开本次不删除已生成的下一次。

新建入口要求紧急/重要至少一项及具体提醒时间，它们映射为原象限字段；保留旧四象限值和编辑能力，不回填或重解释旧任务。旧任务保存、追加记录和草稿不强制新建条件。

关系、重复规则与扩展数据一起进入跨重启草稿和完整备份。新增表也纳入备份摘要，只有目录数据时仍执行每日备份。`app-settings.json` 保存本机启动方式和资源快捷键，不保存认证；也在完整业务备份中。

## 事项与日志扩展

`items` 保存正文、状态、象限、回访、截止、现场和下一步等核心字段。`notes.itemId` 关联同一事项的多条独立记录，追加不覆盖历史。现有 note/progress/request 类型保留；类型标识允许小写字母开头、字母数字下划线或连字符，总长不超过64。界面不识别的类型显示为“其他记录”，保留原标识与内容。只有 progress 更新实际推进时间；查看、修改属性、处理提醒和 AI 均不计推进。

事项和记录各有 `extra` JSON：`{"version":1,"fields":{"futureField":"value"}}`。字段可以是 JSON 对象、数组及基本值，最多10万字符；不接受无效数值或不可序列化值。普通编辑保留未使用字段，显式提交的 fields 按键合并；清空值可保存 null。核心可检索/排序/调度字段需要时以迁移新增正式列。未来增加字段界面时应同步草稿、输入校验、保存反馈和测试；本版没有自定义字段配置器。

草稿保留扩展数据，提交时随事项或记录保存。新版本若改变扩展字段含义、核心状态或必需结构，应提高数据库版本并提供迁移；不能直接重解释旧数据。

`attachments.noteId` 可为空，新增记录的附件保存具体记录归属；旧附件保持任务级归属，不猜测历史来源。收存文件使用相对 data 的路径，原位引用保存外部路径，不移动外部资料。

## 迁移与备份

新版支持0至6的历史结构，升级前备份、事务内迁移、完整性校验成功才更新结构版本。未知更新结构拒绝写入；不能用旧程序覆盖新库。`dataSignature` 继续使用旧便携接续规则，避免更换算法误判旧库变化；完整备份另行对所有用户表校验，包括草稿、提醒及以后新增的表。

备份为独立文件夹：SQLite 一致快照、收存附件、草稿文件和本机设置；不包含 OpenCode 认证、Chromium 缓存和分析运行目录。`backup-manifest.json` 格式版本1，含创建时间、程序/数据库版本、各表记录数、数据摘要以及全部文件的相对路径、长度和 SHA-256。新清单要求文件集合与校验值完全匹配；旧格式备份没有原始校验值时，只能核验当前完整性，预览明确标识。

每日有数据变化时自动备份一次，手动备份可随时执行；备份前等待全部窗口的草稿写入完成，失败不生成成功状态。可选其他磁盘，现有备份不自动清理；同盘备份不能防范整盘损坏。外部引用文件需单独备份。

恢复先核对预览与来源变化，在临时目录校验/迁移，再备份当前完整数据、关闭数据库并切换目录。原目录保留为 `data-before-restore-<UUID>`，恢复过程记录在 data 的同级恢复日志；启动时处理切换中断。恢复回到备份时点，不自动合并后续记录。日常备份位置沿用当前本机选择。

## 提醒

`reminders` 保存事项、回访/截止类型、原到期时间、延后时间和处理状态。以事项+类型+原到期时间去重。启动及唤醒补查、运行时每30秒检查；积压通知合并发送，未处理事项仍保留在工作台。稍后提醒不更改截止或实际推进时间，完成/清除/修改对应时间会取消旧提醒。

通知发出状态先落盘，通知失败不循环弹出；工作台保留未处理入口及当前运行中的失败说明。系统通知不等于用户已阅读或事项已完成。程序完全退出/关机期间不发送通知，下次启动补查。

Windows 使用固定 AppUserModelID 和开始菜单快捷方式，便携版启动时更新为当前程序路径。依据：[Electron 通知说明](https://www.electronjs.org/docs/latest/tutorial/notifications)、[Notification API](https://www.electronjs.org/docs/latest/api/notification)。
